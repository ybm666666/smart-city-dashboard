### 1. 拆包优化：echarts 与 zrender 二次分包

**背景**：Day4 起 `useEcharts.ts` 就已经按需引入（`echarts/core` + 具体 charts / components / renderer），
Day12 实测仍然报出体积告警。

**基线实测**（优化前）：

| chunk | 体积 | gzip |
|---|---|---|
| `echarts-DUILDzbw.js` | 640.91 kB | 213.34 kB |
| `index-*.js` | 36.95 kB | 15.16 kB |
| `AiChatView-*.js` | 21.76 kB | 9.82 kB |

`vite build` 输出：`(!) Some chunks are larger than 600 kB after minification.`

**原因分析**：`manualChunks` 原来只按「包名含 echarts」这一条规则聚合，
而 echarts 依赖的渲染内核 **zrender** 被一并收进同一个 chunk。
zrender 本身体积不小，两者叠加就顶到了 640 kB。

**做法**（`vite.config.ts`）：把 zrender 单独拆出来，形成三层结构

```ts
manualChunks(id: string) {
  if (!id.includes('node_modules')) return
  if (id.includes('zrender')) return 'echarts-zrender'      // 渲染内核，变动极少
  if (id.includes('echarts')) return 'echarts'              // 图表逻辑
  if (id.includes('vue') || id.includes('pinia')) return 'vue'
  return 'vendor'
}
```

**收益**（不只是「过告警线」）：
- **缓存粒度更合理**：zrender 是底层内核，很少随业务变动，可长期缓存；
  业务更新通常只击穿 `echarts` 与页面 chunk，不会连带让 640 kB 整体失效
- **并行下载**：两个包可同时请求，而不是串行等一个大包
- **问题定位更快**：体积异常时能一眼区分是内核还是图表层膨胀

**优化前后对比**：

| chunk | 优化前 | 优化后 | gzip 优化后 |
|---|---|---|---|
| `echarts` | 640.91 kB | 462.47 kB | 155.47 kB |
| `echarts-zrender` | （合并在内） | 180.24 kB | 57.93 kB |
| 构建告警 | ⚠️ 超过 600 kB | ✅ 无告警 | — |

净效果：单包体积从 640.91 kB 降到 462.47 kB，**告警消除**；
总量虽有约 1.8 kB 的分包开销（模块包装），但换来了上述三点长期收益。

### 2. GitHub Pages 部署

**新增文件**：`.github/workflows/deploy.yml`（约 1.1 KB）

- **触发**：`push` 到 `master`；另留 `workflow_dispatch` 支持手动触发
- **权限**：`contents: read` / `pages: write` / `id-token: write`
  （OIDC 部署所需的最小权限集合）
- **并发**：`group: pages` + `cancel-in-progress: true`，
  连续推送时会取消排队中的旧部署，避免把过时产物发上去
- **流程**：
  1. `actions/checkout@v4`
  2. `actions/setup-node@v4`（Node 20，开启 npm 缓存）
  3. `npm ci`（严格按 lockfile 安装，比 `npm install` 更适合 CI）
  4. `npm run build`
  5. `actions/configure-pages@v5`
  6. `actions/upload-pages-artifact@v3`（上传 `dist`）
  7. `actions/deploy-pages@v4`
- **分离 build / deploy 两个 job**：构建失败不会污染部署环境，
  且 `deploy` 通过 `environment: github-pages` 拿到 `page_url`

**base 路径问题**（关键坑）：
GitHub Pages 的项目站点地址是 `https://<user>.github.io/<repo>/`，
如果 `base` 还是 `/`，构建产物里的 `/assets/xxx.js` 会指向
`https://<user>.github.io/assets/xxx.js`（少了仓库名）→ 全部 404。

解决（`vite.config.ts`）：

```ts
base: process.env.GITHUB_ACTIONS ? '/smart-city-dashboard/' : '/'
```

用 `process.env.GITHUB_ACTIONS`（Actions 环境自带）判断：
- CI 中 → `/smart-city-dashboard/`，匹配 Pages 子路径
- 本地 dev / Vercel 等平台 → `/`，不受影响

**为什么不需要 404.html 回退**：项目路由用的是 **hash 模式**（`#/ai` 这种），
路径部分永远只有 `/`，刷新不会向服务器请求深层路径，
所以 GitHub Pages 这种不支持 SPA rewrite 的静态托管也能直接跑。

## 技术要点
- **按需引入 ≠ 分包**：Day4 解决的是「只打包用到的图表类型」，Day12 解决的是
  「打进来的东西怎么切分」。两者互补，前者减总量，后者改粒度
- **缓存命中率比总体积更重要**：拆包后总量略增，但底层内核可长期命中缓存，
  实际用户侧下载量反而更少
- **CI 用 `npm ci` 而非 `npm install`**：前者严格遵循 lockfile 且更快，
  避免 CI 里出现「本地能跑、CI 装的版本不同」的玄学问题
- **`process.env.GITHUB_ACTIONS` 做环境分支**：比维护两份 config 或手改 base 更省心
- **hash 路由对静态托管更友好**：省掉 404 回退，这点在部署前就该确认

补充（Hotfix）：地图页 GeoJSON 403 修复 + 地图尺寸塌陷修复
────────────────────────────────────────

一、线上 403 问题
现象：部署上线后访问 #/map，区县轮廓不渲染，控制台 GeoJSON 请求返回 HTTP 403。
原因：原实现直接外链 geo.datav.aliyun.com 的在线 GeoJSON，该域名在 GitHub Pages
      环境（带 Referer / 跨域策略）下拒绝外链请求，导致地图数据拿不到而白屏。
方案：改为「本地内置 + 运行时异步加载」。
      1) 下载重庆全域 GeoJSON（38 个区县，约 162 KB）到 public/geojson/chongqing.json；
      2) config/mapData.ts 中地图地址改为 `${import.meta.env.BASE_URL}geojson/chongqing.json`，
         自动跟随 vite 的 base 配置，本地开发与 Pages 子路径部署都能正确解析；
      3) hooks/useMap.ts 保持原有逻辑：fetch → echarts.registerMap → sessionStorage 缓存，
         同一 mapName 只注册一次，避免重复请求与重复注册。
收益：不再依赖第三方域名，彻底规避跨域/限流导致的 403；GeoJSON 放 public/ 由浏览器
      按静态资源缓存，不进入主包，主包体积不受影响。

二、地图尺寸塌陷问题（本次随 hotfix 一并修复）
现象：GeoJSON 加载成功、区县数据也注册成功，但地图被压成画布底部一条细带，
      区县轮廓极小，交互几乎不可用。
原因：MapChart 的 height 默认值使用 '100%'，而其外层是 flex 布局中高度由内容派生的
      容器链，百分比高度无法解析出确定值，ECharts 初始化时读到的高度极小。
方案：
      1) MapChart 的 height 默认值改为确定的像素值 '360px'；
      2) .map-chart 增加 min-height: 320px 兜底，避免任何布局变化下再次塌陷。
验证：npm run build 通过（vue-tsc 无类型错误，708 modules，echarts 仍为 462.47 kB）；
      线上 #/map 地图正常铺满，点击区县可联动右侧详情（GDP / 常住人口 / 综合指数 + 产业结构饼图）。
